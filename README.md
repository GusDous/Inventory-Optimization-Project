This project was created to solve what safety stock levels and reorder points should be for purchased components. The outputs are driven by NetSuite fulfillment data via BOM (bill of materials) explosion logic for assembled items and unioned to anything shipped without a BOM associated with it.
The driver to create this project was undue friction caused by inventory stockouts. Prior to this pipeline being created, procurement had to manually, regularly check inventory levels for key components and compare against open work orders and sales orders. There was no easy way within NetSuite's saved search feature to explode BOMs, so process knowledge was heavily relied upon under the old system.
I output the results from my saved searches into csv files which are the bases for the tables created within my database. I then truncate the old data, load the new data, and run my main analytical query. This query first takes the item fulfillment records (how items are shipped from inventory in NetSuite), explodes the assembly items via their bills of material into components, then joins and multiplies those components against how many components shipped each day, and finally unions that output against all the components that were shipped without bill of material records (i.e. components).
There are a few assumptions working simulatneously within my query. The first is that average lead time, variability, is_critical, is_on_blanket_po, non_blanket_lt, and non_blanket_lt_variability were all derived from my process knowledge working in procurement and ordering these components regularly. The thought process behind variability was "What's the longest reasonable number of days this vendor runs late?". This leads into my second assumption: true demand variability and therefore standard deviation of lead times is omitted from v1 for simiplicity reasons. To get an approximate standard deviation of lead time, I simply divide my variability by two within the query. The third that will become moot with time, is that I'm only operating with about 7 months of data. I set up the item fulfillment search to roll over the last year. Since NetSuite has only been live within my organization for about 7 months, that's all the data I have. By October of this year, 2026, we will have a full year of data. I chose to use 1-year rather than two or three to allow for older product lines to roll off quickly.
The result from the pipeline leaves the user with one row per component item, with average daily demand, calculated safety stock and reorder points, and current stock of that item for comparison. I run the pipeline about once a month and adjust safety stock levels and reorder point flags based on the output.
My schema is 5 tables: item_fulfillments, bom_data, assembly_bom_match, component_lead_times, and current_stock. item_fulfillments houses fulfillment data, where demand is derived from. bom_data is where the components live, but they're related to the BOM record, not the assembly record. assembly_bom_match bridges this gap with the BOM ID matched to the assembly ID for it. component_lead times and current_stock both are straightforward, just housing lead times and current inventory positions for each item.
